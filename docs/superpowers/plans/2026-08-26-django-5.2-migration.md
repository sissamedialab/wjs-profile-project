# wjs-profile-project Django 5.2 Migration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make `wjs.jcom_profile` and its six embedded plugins (including `wjs_review`, the
largest sub-component in any of the five `wjs-*` repos) work correctly under Django 5.2, verified
via the real test suite this repo already has, with all four other `wjs-*` repos also ported.

**Architecture:** No structural changes. This is the fifth and last repo in the migration
sequence — its own dependency pins (`Django ~= 4.2`, `wjs_mgmt_cmds ~= 0.5.0`) are what actually
gate the other four repos' new releases from being consumable together. Verification is a full
live test run, not a manual page-check.

**Tech Stack:** Python 3.11+, Django 5.2, `django-upgrade`, `ruff`, `pytest`/`pytest-django`.

**Spec:** `docs/superpowers/specs/2026-08-26-django-5.2-migration-design.md` (this repo).

## Global Constraints

- Python floor: `>= 3.11` (confirmed for all five `wjs-*` repos in this migration effort — this
  repo already declared `python_requires = >=3.10` with `3.10`/`3.11` both in its classifiers, so
  this is a floor *bump*, not a new addition).
- Django target: `5.2`, pinned as `Django ~= 5.2.17` (matching `janeway-5.2`'s own pin exactly).
- No behavioral change.
- `wjs_mgmt_cmds ~= 0.6.0` (completes the cross-repo follow-up from `wjs-utils-project`'s plan).
- Package version bumps to `2.1.0`.
- No changes to `wjs-themes`, `wjs-search-user`, `wjs-submission-project`, or `wjs-utils-project`
  themselves — only consuming their already-bumped versions.
- Leave the second-level security pins (`autobahn`, `cbor2`, `filelock`, `djangorestframework`,
  `pygments`, `ujson`, `click`) unchanged.

Expected outcomes, in order of likelihood — **do not assume success; check which actually
happened:**
1. **All tests pass.** This is the last repo in the sequence — if this passes, all five `wjs-*`
   repos are verified compatible with Django 5.2 together.
2. **Import-time or test failure originating in Hydra** (`wjs/hydra`, cloned by `setup_environment`
   in CI but not installed by Steps 1–3 above in a local run — if Hydra is required and not
   present locally, install/symlink it the same way as the six plugins above, from the sibling
   `hydra` checkout at `/home/yakky/Projects/projects/sissa-1.8/hydra`). If a failure traces to
   Hydra's own code rather than this repo's, record it as an external blocker — Hydra's Django
   5.2 status was assumed compatible (per its integration into `janeway-5.2`'s own history) but
   not independently verified by this plan.
3. **Test failures inside this repo's own code** (`wjs.jcom_profile` core or any of the six
   plugins). These are this repo's responsibility — fix and re-run, following the TDD cycle
   documented in `.claude/rules/tests.md`.

**Two known, pre-existing issues carried forward from `wjs-utils-project`'s final whole-branch
review — neither is a Django 5.2 regression, so don't misattribute a failure here to this port:**

- `wjs-utils-project`'s `import_user_from_wjapp.py` (its `merge_data()` function, around line 471)
  calls `Correspondence.get_or_create(...)` on the model class directly — there's no such
  classmethod on `Correspondence` (defined in this repo, `wjs/jcom_profile/models.py`) — instead of
  the correct `Correspondence.objects.get_or_create(...)`. This will raise `AttributeError`
  whenever that code path runs. Pre-existing in `wjs-utils-project`, unrelated to this repo's own
  code or to Django 5.2.
- That same repo's deferred `wjs_mgmt_cmds/tests.py` verification was earlier (incorrectly)
  attributed to `wjs.jcom_profile.Correspondence` being unimportable. It's actually importable now
  — the real blockers there are missing `pymysql`/`factory_boy` dependencies in that repo. If you
  end up exercising `wjs-utils-project`'s deferred tests as part of closing out this effort, expect
  those import errors (unrelated to anything in this repo) rather than assuming they'll just work
  now that this repo is ported.
