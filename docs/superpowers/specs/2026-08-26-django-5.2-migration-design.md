# wjs-profile-project: Django 5.2 Migration — Design

## Context

This is the fifth and final of five independent `wjs-*` plugin repos being ported to Django 5.2,
following the core `janeway-5.2` migration (Django 4.2.30 → 5.2.17, Python floor `>=3.9` →
verified `3.10`–`3.13`) on branch `migration/1.8-phase7-pep440-compat-release`, and after
`wjs-themes`, `wjs-search-user`, `wjs-submission-project`, and `wjs-utils-project` (see their own
specs, in their respective repos' `docs/superpowers/specs/2026-08-26-django-5.2-migration-design.md`).

This repo is the largest of the five (326 `.py` files) and the only one with an explicit
`Django ~= 4.2` pin today. It bundles `wjs.jcom_profile` itself (150 files: profile fields,
newsletter, dashboard) plus six embedded Janeway plugins under `wjs/plugins/`: `wjs_home_blocks`
(8 files), `wjs_latest_articles` (8), `wjs_latest_news` (9), **`wjs_review`** (122 — the single
largest sub-component in any of the five repos, the peer-review workflow), `wjs_stats` (7),
`wjs_subscribe_newsletter` (8).

**Correction to `wjs-utils-project`'s spec:** that spec stated `plugins.wjs_review` is "a Janeway
plugin entirely outside this 5-repo migration's scope." That was wrong — `wjs_review` lives inside
*this* repo, so it is in scope. Fixed there in a follow-up commit alongside this spec.

**Amendment (at planning time):** the Python floor across all five repos is now confirmed as
**3.11**. This repo's existing `python_requires = >=3.10` (see Repo shape below) was accurate
against the floor assumed when this spec was written, but now needs bumping to `>=3.11` — a new
change not in the original Changes list, added in the implementation plan's Task 2.

## Goal

Make `wjs.jcom_profile` and its six embedded plugins work correctly under Django 5.2, with no
behavioral change, verified via the real test suite this repo already has, run against the
already-migrated `janeway-5.2` checkout with all four other `wjs-*` repos also ported.

## Repo shape (as found)

- `setup.cfg`: package `wjs.jcom_profile`, version `2.0.27.dev1`, `python_requires = >=3.10`
  (classifiers list `3.10` and `3.11` — no floor conflict found here, unlike
  `wjs-submission-project`'s `StrEnum` issue). `install_requires` pins `Django ~= 4.2` explicitly
  — the only one of the five repos to do so — plus a long list of second-level security pins
  (`autobahn~=25.10`, `cbor2~=5.9.0`, `filelock ~= 3.20.3`, `djangorestframework ~= 3.17.1`,
  `pygments ~= 2.20.0`, `ujson ~= 5.13.0`, `click ~= 8.3.3`), `wjs-themes >= 2.0.18`, and
  `wjs-submission >= 2.0.16`. `[options.extras_require] test` pins `pytest-django ~= 4.12.0` with
  a comment identical in spirit to `wjs-submission-project`'s: "4.13 requires Django>=5.2, we're
  on Django~=4.2" — and `wjs_mgmt_cmds ~= 0.5.0`, the tight pin flagged as a cross-repo follow-up
  in `wjs-utils-project`'s spec.
- A repo-wide grep for the same deprecation patterns checked in every prior repo
  (`CheckConstraint`, `index_together`, `ugettext`, `force_text`, `is_ajax()`,
  `django.utils.six`, `django.conf.urls.url`, `providing_args`, `assertQuerysetEqual`, `StrEnum`,
  `USE_L10N`) found **one hit, confirmed to be a false positive**: `wjs/defaults/settings.py`
  defines a local no-op `def ugettext(s): return s` shim used only to statically declare the
  `LANGUAGES` setting's display names — not an import of Django's removed
  `django.utils.translation.ugettext`. No `StrEnum` or other Python-3.11+-only syntax found
  anywhere in this repo.
- **Real test suite**, and the *source* of the shared CI test template:
  `.gitlab-ci-run-tests.yml` in this repo defines the `.run-tests` job that
  `wjs-submission-project`'s own CI includes by reference (`project: 'wjs/wjs-profile-project'`).
  Local workflow (documented in this repo's `.claude/rules/tests.md`, same pattern as
  `wjs-submission-project`'s): `pip install -e .[test]` into a host Janeway checkout, then
  `pytest --create-db -n7 ../../wjs-profile-project` from `janeway/src`.
  `DJANGO_SETTINGS_MODULE = wjs.defaults.tests`; tests live in both `wjs/jcom_profile/tests/` and
  `wjs/plugins/wjs_review/tests/` — so a live run exercises `wjs_review` directly, not only
  statically. The full suite takes 10+ minutes even with `-n7`, per that same file.
- CI (`.gitlab-ci.yml` + `.gitlab-ci-run-tests.yml`) has the same stale-image situation as
  `wjs-submission-project`: the test job runs against
  `registry.gitlab.sissamedialab.it/wjs/janeway/debian-python-git-janeway:${JANEWAY_VERSION}`,
  `JANEWAY_VERSION` defaulting to `"production"` — a pre-migration build. Additionally, CI clones
  a third-party plugin, **Hydra** (`wjs/hydra.git`, ref `wjs-production`) via `setup_environment`.
  Hydra already appears integrated into `janeway-5.2`'s own git history (its commit log shows
  `Use Hydra for errata & co.` and a Hydra integration merge), and a `hydra` checkout exists as a
  sibling directory locally — so it's likely already Django-5.2-safe, but that isn't independently
  confirmed by this spec.
- Default CI image is `python:3.11` (used by the `Pre-commit`/lint job; the test job uses the
  separate Janeway image above, unaffected by this default).

## Approach

Same tool-assisted method as the prior four repos (`django-upgrade --target 5.2` + `ruff`). Given
this repo's scale — 326 files including a 122-file sub-plugin — manual review is
tooling-output-driven and spot-checked rather than exhaustive; the live test suite (which already
covers `wjs_review` directly) is what actually validates correctness here, not a file-by-file
read. This mirrors how `wjs-submission-project`'s spec scoped its own, smaller-scale version of
the same trade-off.

Considered and rejected:
- **Full manual read of all 326 files before writing any code**: rejected as disproportionate —
  the deprecation-pattern grep came back clean (one confirmed false positive), and this repo has
  genuine automated test coverage, including of `wjs_review`, to catch what a grep can't.
- **Treat this repo's port as blocked until Hydra's Django 5.2 status is independently verified**:
  rejected — Hydra's integration into `janeway-5.2`'s own history is reasonable evidence it's
  already handled; if the live test run surfaces a Hydra-side failure, that's tracked as an
  external blocker at that point, not assumed upfront.

## Changes

1. **Python fixes** across the repo (`wjs.jcom_profile` core + all six plugins) as found by
   `django-upgrade --target 5.2` + spot-checked manual review. Scope is whatever those
   tools/review turn up; expected small given the clean grep sweep.
2. **`setup.cfg`**:
   - `Django ~= 4.2` → `Django ~= 5.2.17`, matching `janeway-5.2`'s own `requirements.txt` pin
     exactly (`Django~=5.2.17`).
   - `pytest-django ~= 4.12.0` → drop the ceiling. The documented reason was Django-4.2-specific
     (same reasoning as `wjs-submission-project`'s identical change); running on Django 5.2
     removes it.
   - `wjs_mgmt_cmds ~= 0.5.0` → `wjs_mgmt_cmds ~= 0.6.0`, completing the cross-repo follow-up
     `wjs-utils-project`'s spec flagged when it bumped its own version to `0.6.0`.
   - `wjs-themes >= 2.0.18` and `wjs-submission >= 2.0.16` are already satisfied by those repos'
     new `2.1.0` releases — no change needed.
   - Bump `version` from `2.0.27.dev1` to `2.1.0`, for consistency with the other four repos —
     lower priority than the others since nothing in this 5-repo set pins `wjs.jcom_profile` by
     version.
   - Leave the second-level security pins (`autobahn`, `cbor2`, `filelock`,
     `djangorestframework`, `pygments`, `ujson`, `click`) alone — unrelated to Django 5.2
     compatibility, out of scope for this port.
3. **`.gitlab-ci.yml`**: bump the default `python:3.11` image to `python:3.13`, matching the
   established pattern from `wjs-themes`/`wjs-search-user`. This only affects the `Pre-commit`/lint
   job — the test job's separate Janeway Docker image (flagged below) is untouched.
4. Flagging, not fixing: the stale `JANEWAY_VERSION: "production"` Docker image (same situation as
   `wjs-submission-project`, since both share this CI template) — out of scope, a `janeway-5.2`
   release concern.
5. No changes to `wjs-themes`, `wjs-search-user`, `wjs-submission-project`, or `wjs-utils-project`
   themselves — only consuming their already-bumped versions here.

## Verification

1. Run `django-upgrade --target 5.2` and `ruff` over the repo; apply and review fixes.
2. Spot-check higher-risk areas manually, prioritizing `wjs_review` (the largest sub-plugin) and
   `wjs.jcom_profile`'s core profile/dashboard/newsletter code.
3. `pip install -e .[test]` this repo into the `janeway-5.2` checkout's virtualenv.
4. Confirm `wjs-themes`, `wjs-search-user`, `wjs-submission-project`, and `wjs-utils-project` are
   all also editable-installed into the same venv — this is the last repo in the sequence, so
   everything else should already be ready.
5. Symlink each of the six plugins (`wjs_home_blocks`, `wjs_latest_articles`, `wjs_latest_news`,
   `wjs_review`, `wjs_stats`, `wjs_subscribe_newsletter`) into `janeway-5.2/src/plugins/`.
6. From `janeway-5.2/src`, run the test suite (`wjs/jcom_profile/tests/` and
   `wjs/plugins/wjs_review/tests/`), per this repo's own documented local workflow. Given the
   documented 10+ minute full-suite runtime, prefer targeted selectors during iterative fixing and
   reserve a full run for the final check.
7. **Honest caveat, not an assumption of success**: if a failure traces to Hydra's own code rather
   than this repo's, that's tracked as an external blocker, not treated as a defect introduced
   here (see Repo shape above).

## Out of scope

- Fixing Hydra if the live test run surfaces it as not yet Django-5.2-safe (tracked, not fixed,
  as an external blocker).
- Publishing a Django-5.2-compatible Janeway CI Docker image (a `janeway-5.2` release concern).
- Porting `wjs-themes`, `wjs-search-user`, `wjs-submission-project`, or `wjs-utils-project` — all
  four already have their own completed specs.
- The `wjs-utils-project` spec correction regarding `wjs_review`'s scope — handled as its own
  follow-up commit in that repo, not part of this spec's implementation.
- Tightening the second-level security dependency pins (`autobahn`, `cbor2`, `filelock`,
  `djangorestframework`, `pygments`, `ujson`, `click`).
